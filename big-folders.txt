WHAT WAS MEASURED AND HOW
- Release builds of upstream main dd39e3b ("main") and of big-folders b2784b31 ("branch"; later commits are the
  merge of network-deep and lint-only changes), run as the tester user on a private Xvfb (no window manager),
  private D-Bus session and disposable HOME, with fictional folders created by a script:
  "Files 10000/50000/100000" (Sample document NNNNNN.<txt|pdf|odt|ods|png|jpg|mp3|zip|csv|md>, random dates over
  four years), "Mixed 100000" (every tenth item a folder), "Long names 10000" (~150-character names), on local
  ext4 disk (/var/tmp) and on tmpfs (/dev/shm).
- Real X input with xdotool (XTEST): the folder is typed into the address bar (Ctrl+L, Enter), column headers and
  menus are clicked, keys are pressed, the scroll bar and a rubber band are dragged.
- "stall" = the longest time GTK's main loop took to answer a _NET_WM_PING sent every 20 ms (the window could not
  react to input for that long). "busy" = until the app's CPU use dropped below 3% for 0.5 s (includes that
  0.5 s). First rows = first time text appears in the first row of the list (pixels read from the window).
  Memory = VmRSS. GTK criticals/warnings are collected from the app's log for the whole run.
- Same scenario at 1x and 2x (GDK_SCALE=2) and in Compact view (View > Show > Compact view).
- weston 13 (headless backend, Wayland, no Xwayland on this machine): xdotool cannot drive Wayland clients, so only
  launch + listing + criticals were checked. 100,000 files, time until idle / CPU / RSS:
    main   1x 7.6 s / 8.1 s / 561 MB   2x 8.7 s / 10.9 s / 586 MB   no criticals
    branch 1x 2.9 s / 4.8 s / 486 MB   2x 3.4 s / 5.5 s / 516 MB   no criticals
- Profiles: perf with GTK/GLib debug symbols from Ubuntu's debuginfod. Main, opening 100,000 files: 4.9 s of
  interface-thread CPU, 2.1 s of it GTK's TreeListModel rebuilding every node per batch (expandable folders are off
  by default), 0.9 s GtkFilterListModel bitset searches, 0.5 s building rows (entry_from_info) on the main loop.
  Select all: ~80% splitting/decoding every selected address for the command bar (selection_facts), repeated per
  command refresh. Group by Type: the regroup went through "no section sorter", heading each item as its own group
  (100,000 GroupSlot objects with weak refs to one model -> "Too many GWeakRef registered").
